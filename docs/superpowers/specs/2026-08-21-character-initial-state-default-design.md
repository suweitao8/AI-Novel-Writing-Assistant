# 角色资产默认初始状态设计

## 背景

角色资产的后续外貌、图片和音色都以状态为来源。当前服务端在角色缺少状态时已有兼容兜底，但手动创建角色时，前端初始状态卡片的描述和图片提示词仍可能为空，导致用户看到的角色像是只有基础身份、没有可用的第一版状态。

## 目标

1. 任意入口创建角色资产后，持久化数据都至少包含一个有内容的“初始状态”。
2. 手动创建时不要求用户先填写外貌、图片提示词或音色提示词；系统根据姓名、性别和默认年龄段生成可直接编辑与生成资产的基础状态。
3. 设定中心、漫剧参考提取、脚本侧快速创建、AI 设定包落库和服务端 API 使用同一套默认状态规则。
4. 初始状态始终是状态列表第一项且不可删除；后续状态仍由用户手动创建并继承上一状态。

## 方案

### 统一默认状态工厂

在共享状态契约层提供角色专用的默认状态构造函数。输入可以包含姓名、性别、年龄段以及已有外貌/体型/服装/面部/音色信息；缺失信息使用稳定的中文模板补齐：

- `label`: `初始状态`
- `ageGroup`: 输入年龄段，否则 `youth`
- `description`: 优先使用已有外貌信息，否则生成“姓名 + 年龄段 + 性别 + 常态外观”的基础描述
- `imagePrompt`: 优先使用已有面部/图片提示词，否则使用完整身份与初始外观描述
- `voicePrompt`: 优先使用已有音色信息，否则使用性别与年龄段对应的自然清晰音色描述
- `referenceStateId`: `null`

该工厂只负责稳定的本地默认值，不在创建角色时额外调用 AI，避免模型失败阻断角色创建。AI 草稿提供更具体的字段时，仍由这些字段覆盖模板值。

### 服务端权威归一化

角色创建 API、AI 批量设定包持久化和旧数据读取统一调用默认状态工厂。即使客户端漏传 `states` 或传入空白首状态，服务端也必须写入完整的初始状态；返回 DTO 中也必须包含该状态，避免不同入口形成不同数据契约。

### 前端预填

设定中心手动创建弹窗和漫剧快速创建弹窗打开时，直接显示默认状态内容。用户可以继续编辑，但不需要为了保存角色而填写状态字段。保存成功后，服务器返回的状态作为最终值回填。

### 后续状态

新增状态沿用现有逻辑：默认继承上一状态，用户填写状态名称和变化描述即可；初始状态禁止删除或作为其他状态的引用目标。此需求不自动根据章节内容创建后续状态。

## 非目标

- 不删除 `Character` 旧外貌、体型、服装和音色字段；它们继续作为历史兼容数据。
- 不新增数据库表或执行破坏性迁移。
- 不在创建角色时强制调用 AI 生成详细人物小传。
- 不改变状态图片、音色的独立生成、重试和并发保存逻辑。

## 测试与验收

- 共享类型测试：无输入时得到非空描述、图片提示词、音色提示词和青年初始状态；有旧字段时优先保留旧字段内容。
- 服务端测试：创建 API、AI 批量落库和列表回退均返回一个有内容的首状态；客户端不传状态时服务端仍持久化首状态。
- 客户端测试：手动创建和快速创建初始状态不为空，初始状态仍不可删除，后续状态可继续手动新增。
- 回归检查：shared/server 构建、客户端类型检查和角色状态聚焦测试。

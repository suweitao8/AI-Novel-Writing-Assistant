# 场景空间标记与投射中心可视化设计

## 背景

场景状态图是 2:1 等距柱状全景图，当前识别流程让模型同时猜测物体的米制世界坐标和图像区域。实际数据已经证明，模型能够指出门、窗、桌椅的大致图像区域，但直接猜出的世界坐标会把物体放到全景图的另一侧：例如源图右侧的房门被保存到 `+X/+Z`，而按全景图经度它应位于 `+X/-Z`。这不是 PlayCanvas 画框本身的问题，而是视觉证据没有成为空间映射的权威来源。

此外，编辑器没有明确显示投射中心，用户难以判断高度基准和标记相对全景图的方向。投射中心必须像 Unreal HDRIBackdrop 一样成为一个清晰、不可选中的方形/晶体参考体，并显示从地面到中心的高度线。

## 目标

- 让可见的 `imageRegion` 成为固定场景物体水平角度的权威证据。
- 保留已有世界半径作为深度近似，避免把单张全景图误认为可以测得真实深度。
- 读取旧数据时即时纠正明显的经度侧错误；新识别写入时保存纠正后的坐标。
- 场景 3D 编辑器和分镜 3D 草图复用同一套空间标记与投射中心可视化。
- 确保本地 Grok 文本桥真正把多模态图片内容送给视觉模型，而不是只把图片 URL 丢进文本 transcript。

## 非目标

- 不把空间标记升级成精确测绘、碰撞检测或自动重建完整房间网格。
- 不通过关键词、固定房间模板或固定坐标替代视觉模型识别。
- 不要求用户为历史场景重新执行识别，也不修改数据库中的原始图片制品。
- 不新增场景类型或镜头级环境参数。

## 设计决策

### 1. 图像区域到水平角度

对每个带 `imageRegion` 的 AI 标记，取归一化等距柱状图区域中心 `u = x + width / 2`。以当前全景坐标契约为准：`u=0.5` 是水平正前方，图像向右绕到世界 `+X` 后再进入 `-Z`。服务端用确定性公式把 `u` 映射为水平径向方向：

```text
angle = (1 - u) * 2π - π/2
direction = [cos(angle), sin(angle)] // world X/Z
```

这样源图右侧的房门会落在 `+X/-Z`，源图左侧的窗会落在 `-X/+Z`。墙面标记的 `yawDeg` 同步朝向该径向方向；地面物体保留模型给出的自身朝向，只纠正位置方向。

### 2. 深度与兼容性

单张等距柱状图不包含可靠的绝对深度。水平半径优先沿用已有 marker 的 `position.x/z` 半径；若没有有效半径，则使用当前场景半径上限的保守比例作为临时深度。这样修正“在全景图哪一侧”，不会伪造精确测距。

- 没有 `imageRegion` 的旧 AI 标记保留原坐标，只继续做原有范围裁剪和落地。
- `source: "manual"` 的标记不被视觉投影覆盖，用户手工修正具有最高优先级。
- 归一化在公共服务端读取、空间识别写入和分镜自动构图上下文三个入口执行，保证页面、保存数据和下游 Prompt 一致。
- 归一化设计为幂等；已经修正的数据再次读取不会继续漂移。

### 3. 投射中心参考体

在共享 PlayCanvas viewer 中增加环境级 gizmo：

- 一个半透明、带发光边缘的方形晶体/立方体，中心固定在 `[0, projectionCenterHeight, 0]`。
- 一个从地面原点延伸到晶体中心的细竖线，用来表达当前投射中心高度。
- gizmo 不进入角色或空间标记的拾取集合，不可选、不保存到 `layout3d`，只反映当前环境设置。
- 高度滑块改变环境预览时，晶体和竖线立即更新；默认仍使用环境运行时的 `2` 和 `15`（字段名 `domeRadius` 的用户语义为半球直径）。

## 数据流

```text
状态图 + 环境参数
        │
        ├─ 多模态 Prompt：识别物体 + 必填 imageRegion
        │        │
        │        └─ server projection：u → X/Z，半径保守继承，墙面 yaw 修正
        │
        ├─ StorySettingsProjection：读取旧 marker 时即时同样归一化
        │
        └─ DramaShotBlockingSketchService：构图上下文使用同一份归一化 marker

scene3dEnvironment
        └─ shared viewer：HDRI + projection-center gizmo + scene marker boxes
```

本地 Grok bridge 的多模态请求使用 JSON Prompt 传输。内联 base64 图片先物化为短生命周期临时文件，再以 ACP 资源链接交给 Grok CLI；CLI 参数中不出现超长 base64，也不在临时文件之外留下资产副本。原有文本请求仍使用同一条 bridge。

## 验证标准

- 单元测试覆盖 `u=0.5` 正前方、右侧门 `u≈0.81`、左侧窗 `u≈0.45`、缺失区域、手工标记和重复归一化。
- 服务端测试证明读取旧场景会纠正经度侧，识别保存和分镜构图上下文使用同一结果。
- bridge 测试证明多模态消息变成 `--prompt-json` 的资源链接，且不会把 base64 作为 CLI 参数。
- 前端契约测试证明投射中心 gizmo 创建、更新、绘制和销毁接入共享 viewer。
- 使用当前真实场景在浏览器中刷新场景 3D 编辑器和分镜 3D 草图，检查投射中心方形/高度线可见，房门、窗、桌椅的方向与源全景图一致，并确认控制台没有新增运行时错误。

## 风险与取舍

如果模型返回的区域框本身不准，确定性投影只会忠实放大该视觉误差；因此 Prompt 要求每个标记必须有真实图片证据，不能只依赖文字描述。绝对距离仍是近似值，产品层继续把空间标记定位为构图参照，不把它当作精确几何。

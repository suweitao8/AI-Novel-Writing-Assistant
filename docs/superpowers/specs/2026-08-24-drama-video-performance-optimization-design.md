# 漫剧整集视频合成性能优化设计

## Background

当前整集合成以 Remotion 作为唯一画面时间轴，FFmpeg 负责配音规范化、最终音视频封装和成片探测。这个职责划分正确：不会重新逐镜编码再拼接，也能以统一的 720P 或 1080P 渲染配置校验最终成片。

但执行链路仍有三个与成片质量无关的串行等待点：

- 每个镜头按顺序写入配音、执行 ffprobe、查找静态画面或提取视频首帧；
- 每个标题、镜头、片尾分段按顺序启动一个 FFmpeg 音频规范化进程；
- Remotion 配置固定为 2 个并发渲染 worker，未利用开发机可用的多核资源。

以近期 84 秒的 720P 成片为例，FFprobe 已确认其为 1280×720、24fps 的 H.264/AAC MP4；本次优化必须保持该输出合同，并且不能改变镜头顺序、真实配音时长、字幕时轴或当前的字幕视觉样式。

## Goals

- 在不降低分辨率、帧率、编码格式、音频格式或字幕效果的前提下缩短整集合成的墙钟时间。
- 将独立的本地 I/O、ffprobe 和音频规范化工作改为有上限的并发任务，避免一次启动过多 FFmpeg 进程。
- 让 Remotion 在当前多核开发机上使用合理的渲染并发，并允许通过环境变量保守覆盖。
- 将准备、音频、渲染、封装四个阶段的耗时写入任务进度，便于后续以真实数据评估收益。
- 保持失败语义：任一必要音频、画面准备或渲染步骤失败时不产出伪成功成片；可恢复的缺画面仍只作为 warning。

## Non-goals

- 不改变 720P 开发、1080P 最终输出的全局分辨率选择。
- 不改变 Remotion 作为整集唯一画面渲染器，也不恢复逐镜 FFmpeg 编码和 concat。
- 不修改字幕内容、旁白前缀规则、白字模糊阴影样式或镜头画面表现。
- 不并行整集成片渲染任务；同一集现有的单任务互斥继续有效，避免多个高负载 Remotion 进程竞争资源。

## Decision

### 1. 视频处理专属受控并发器

在 `server/src/services/drama/video/` 内新增归属明确的并发策略模块。它提供：

- 预处理默认并发数：3；
- 媒体拷贝默认并发数：4；
- 环境变量仅可在安全范围内覆盖，非法值回退默认值；
- 按输入序号收集结果，保证即使任务完成顺序不同，镜头、字幕与音频仍按原镜头顺序进入时间轴。

镜头计划（音频写入、ffprobe、已有视频首帧提取）使用预处理并发器；每个镜头内部的台词仍按 `lineIndex` 顺序探测。这样可以并行独立镜头，却不改变一个镜头内的真实配音播放顺序。

任务进度的写入通过一个串行写入队列提交，避免并发 worker 中较早的数据库请求在较晚进度之后落盘，造成进度回退。

### 2. 并行音频规范化，串行最终拼接

标题静音、每镜头音频以及片尾静音互相独立，改用预处理并发器生成固定命名的 WAV 文件。所有单段 WAV 完成后，仍用一个 FFmpeg concat 命令按原 segments 顺序生成整集音轨。

这保留了原有 44.1 kHz、双声道 PCM 规范化和精确的时间线对齐；只减少互不依赖的 FFmpeg 进程等待时间。

### 3. Remotion 并发与渲染热路径

Remotion 默认 worker 从 2 提升到 4，并允许 `DRAMA_REMOTION_CONCURRENCY` 覆盖。值被限制在 1 至 8 之间，防止配置错误耗尽机器资源。整集渲染在音频预处理完成后才启动，因此不会和多个预处理 FFmpeg 进程叠加争抢 CPU。

字幕轨已按时间排序。渲染组件将从“每帧线性扫描全部字幕”改为二分查找当前 cue，减少长视频中随字幕数量增长的重复 JavaScript 工作；没有激活字幕时仍返回空层。

### 4. 阶段耗时可观测性

`DramaBatchJob.progress` 增加可选的 `timings`：准备、音频、渲染、封装的毫秒耗时以及作业总耗时。时间戳仅作为运行诊断数据，不参与镜头时长、成片时间轴或任何用户内容判断。

每次阶段切换只在前一阶段完成后记录耗时，失败路径也保留已完成阶段的耗时，便于判断瓶颈所在。

## Module Boundaries

- `video/videoProcessingConcurrency.ts`：视频处理的受控并发、环境变量解析和有序映射；不依赖数据库或 Remotion。
- `video/DramaEpisodeAssemblyService.ts`：镜头计划调度、作业进度顺序写入与阶段计时。
- `video/DramaRemotionEpisodeAssembler.ts`：受控并发的分段音频规范化，最终 concat、mux、探测保持串行。
- `video/DramaRemotionRenderer.ts` 与 `video/remotion.config.ts`：Remotion worker 配置和渲染过程。
- `video/src/DramaEpisodeVideo.tsx`：仅负责当前字幕 cue 查找与呈现，不感知后端并发策略。

## Testing and Acceptance

- 并发器测试：限制生效、输出稳定保持输入顺序、任一 worker 错误会失败且不会产生乱序结果。
- 整集合成测试：多个分段音频可并发规范化，但最终 concat 列表保持原顺序；最终 mux 仍复制 Remotion 视频流。
- 作业服务合同测试：镜头计划通过受控并发构建，进度写入不会倒退，阶段耗时会持久化。
- Remotion 配置与组件测试：默认并发为 4、环境变量有边界；字幕 active cue 的二分查找与原时轴语义一致。
- 回归：现有 720P 与 1080P 合同测试通过；使用 FFprobe 验证输出仍为目标分辨率、24fps、H.264 视频与 AAC 音频。

## Rollout

1. 先加入并发器和测试，再接入镜头计划与音频规范化。
2. 加入任务阶段计时与 Remotion 并发配置。
3. 优化字幕查找，并运行视频模块的单元、合同和 TypeScript 校验。
4. 运行本地 Remotion/FFmpeg smoke 成片，使用 FFprobe 校验产物合同。
5. 合并到 `main` 后保留环境变量覆盖能力；如果某台机器资源紧张，可把 `DRAMA_REMOTION_CONCURRENCY` 调低至 1 或 2。

# 角色推断身高与分镜比例基准设计

## 背景

当前 PlayCanvas 3D blocking viewer 为所有代理角色使用同一个约 1.8 米的基础缩放。角色虽然可以在单镜头里手动放大或缩小，但角色资产本身没有可复用的比例基准，因此儿童、高个角色和普通成年人在不同镜头中容易出现忽大忽小的情况。角色设定中已有性别、年龄段、体型、外貌、剧情定位等信息，适合由结构化 AI 推断一个用于视觉 blocking 的大致身高。

## 目标与非目标

### 目标

1. 在角色资产上持久化一个可解释的近似身高档案，而不是让每次打开分镜时重新随机判断。
2. 推断使用角色的结构化设定与描述，由 Prompt Registry 中的结构化 PromptAsset 完成；不使用关键词表或硬编码人物类型作为核心推理逻辑。
3. 3D blocking viewer、AI 自动构图和保存/重新打开布局共用同一个角色级比例基准。
4. 让大高个、儿童/少年和普通成年人在同一镜头及跨镜头中保持稳定的相对高度。
5. 兼容既有分镜布局：没有身高元数据的旧布局继续按原来的绝对缩放打开，不因为本次升级被静默改写。
6. 在设定中心能看到已经生成的只读比例基准，但不把估算值伪装成用户手工确认的精确身高。

### 非目标

- 不把身高变成角色表单里的手工输入项。
- 不修改角色图片、四视图裁切、场景 HDRI 或道具预览逻辑。
- 不让每个镜头保存一份新的“角色身高”；镜头只保存当时使用的身高元数据和用户对基础比例的手动调整结果。
- 不要求对历史所有角色一次性批量调用模型；估算在相关角色第一次进入 3D blocking 时按需完成。

## 方案选择

### 方案 A：每次分镜打开时临时推断

实现成本低，但同一角色在不同镜头之间可能因模型输出波动而变化，也无法追溯某次比例的来源。放弃。

### 方案 B：在角色创建/编辑时同步调用模型

比例稳定，但会让普通角色保存操作依赖一次 LLM 调用，保存延迟、失败恢复和批量导入都会变复杂。放弃。

### 方案 C：角色级缓存 + 3D blocking 首次使用时按需补齐（采用）

把估算档案放在角色资产上；进入 3D blocking 时只为缺失或输入指纹已变化的角色推断并缓存。之后所有镜头读取缓存。对旧布局保留兼容分支，对新布局记录使用过的身高，以便在角色档案变化时按比例换算，而不是重置用户的手动缩放。

## 数据模型

在小说 `Character` 与独立短剧 `DramaCharacter` 上各增加可空 `heightProfileJson` 字段，保持两种来源的角色都能使用同一套 blocking 规则。字段值是版本化 JSON：

```json
{
  "schemaVersion": 1,
  "heightMeters": 1.72,
  "confidence": 0.78,
  "rationale": "成年女性，设定为中等体型，描述没有极端身高特征。",
  "source": "ai",
  "inputFingerprint": "sha256:...",
  "generatedAt": "2026-08-26T00:00:00.000Z"
}
```

约束如下：

- `heightMeters` 经过结构化 schema 与服务层双重限制，范围为 0.50–10.00 米，允许怪物和巨型生物参与稳定的相对比例计算。
- `confidence` 范围为 0–1。
- `source` 为 `ai` 或 `fallback`。`fallback` 只用于模型不可用、输出损坏等安全兜底，固定为 1.8 米并明确标记为非 AI 结果；不参与角色类型推断。
- `inputFingerprint` 由角色名称、剧情定位、性别、年龄段、体型、外貌、性格、背景、服装和面部提示词等参与推断的字段规范化后计算。字段未改变时复用档案，避免重复调用和随机漂移。
- JSON 解析失败时不覆盖原始字段；服务层只接受完整且在边界内的档案。

## Prompt 与推断服务

新增 `novel.character.heightEstimate@v1` PromptAsset，注册到 Prompt Registry。Prompt 输入是经过筛选的角色 JSON，输出为 `heightMeters`、`confidence` 和简短 `rationale`。系统提示明确要求：

- 先使用年龄段、体型、外貌和角色描述进行整体判断；儿童/少年可以明显低于成年人，高个或矮小特征应反映在结果中。
- 未提供证据时给出保守的常见范围内估计，不把姓名、性别刻板印象或单一职业当作身高证据。
- 结果是用于 3D 相对比例的近似值，不宣称是事实测量值。
- 只输出 schema JSON。

新增 `CharacterHeightProfileService`，职责限定为角色 blocking 比例档案：

1. 查询指定小说角色或短剧角色的参与字段与现有档案。
2. 根据输入指纹复用有效档案；缺失或指纹变化时调用注册 Prompt。
3. 对同一进程内同一角色的并发请求合并，避免同一页面同时打开多个镜头产生重复调用。
4. 使用角色行的 `updatedAt` 和旧 `heightProfileJson` 做条件更新，避免慢完成的推断覆盖并发编辑后的新资料。
5. AI 调用或结构化输出失败时返回并持久化 1.8 米 `fallback` 档案，使 blocking 仍可用，同时保留来源标记，便于后续重试/观测。

## 分镜数据流与兼容规则

### 服务端上下文

`DramaShotBlockingSketchService.getEditorContext` 在构建角色列表时确保角色档案存在，并把以下只读数据传给客户端和自动构图 Prompt：

```ts
{
  characterName: string,
  heightMeters: number,
  heightSource: "ai" | "fallback" | "legacy",
  heightConfidence?: number,
  ...existingAssetFields
}
```

小说导入项目读取小说 `Character`；独立短剧读取 `DramaCharacter`。没有可关联角色资料时使用 `legacy` 的 1.8 米，仅作为旧项目兼容值。

### AI 自动构图

自动构图输入会携带每个角色的 `heightMeters` 和比例来源，并明确要求 `scale` 表示镜头构图的局部调整，不得用它抹平角色之间的身高差。服务端在归一化 AI 输出时以角色基础比例换算实际代理模型缩放，防止模型返回的绝对值覆盖角色档案。

### PlayCanvas viewer

代理模型原生高度约为 1.8287 米，基础 local scale 由以下公式得到：

```text
baseScale = heightMeters / 1.8287
actualScale = baseScale × shotScaleMultiplier
```

首次加入角色使用 `shotScaleMultiplier = 1`。现有缩放按钮继续修改实际缩放，因此用户仍可为镜头构图做局部调整。viewer runtime 为每个 actor 保留 `heightMeters`，导出布局时写入可选的 `heightMeters` 字段。

### 已保存布局兼容

- 旧布局 actor 没有 `heightMeters`：按保存的 `scale` 原样加载，保持已有镜头画面不变。
- 新布局 actor 有 `heightMeters`：若当前角色档案高度变化，按 `currentHeight / savedHeight` 等比换算三轴 scale，保留用户的手动缩放比例。
- 保存时永远写入当前 `heightMeters`；因此旧布局第一次保存后自然升级为带比例元数据的布局。
- `schemaVersion` 继续为 1，因为新增字段是可选兼容字段，不改变已有必填结构。

## 用户界面

设定中心角色资产在已有角色详情中增加只读“分镜比例基准”信息：有档案时显示“约 X.XX 米”和“AI 估算/兼容基准”；没有档案时不触发模型调用，也不显示虚假的精确值。3D blocking 页面保留现有位置、缩放和保存交互，不增加手工身高输入，避免用户把近似值误认为硬事实。

## 错误处理与稳定性

- Prompt schema、服务层范围检查和布局归一化共同阻止异常数值进入 3D runtime。
- LLM 不可用时使用明确标记的 1.8 米 fallback，页面不因比例推断失败而卡死；下一次输入指纹仍可重新尝试 AI 推断。
- 条件更新失败时重新读取角色资料，优先使用并发操作已经写入的档案，避免丢失最新角色编辑。
- 任何旧布局缺少新字段都走兼容分支，不进行破坏性数据库重置或快照重写。

## 验证标准

1. 单元/契约测试覆盖：档案解析、边界限制、指纹复用、fallback 标记、旧布局加载语义和带身高布局的等比换算。
2. 服务测试验证自动构图输入包含角色高度、输出不会遗漏角色，且 AI 返回的构图调整不会覆盖角色基础比例。
3. 前端类型检查和现有 blocking 3D 契约测试通过。
4. 在真实分镜页面验证至少三类角色（大高个、普通成年人、儿童/少年）在同一镜头中的相对高度，并关闭/重新打开同一镜头确认布局不漂移。

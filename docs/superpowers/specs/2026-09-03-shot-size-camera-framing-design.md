# 分镜景别取景一致性设计

## 背景

自动构图服务已经根据镜头的景别生成 `layout3d.camera`，并把特写、近景、中景、全景和远景映射到不同的取景参数。当前 3D 草图页面加载布局后又无条件调用编辑器的 `fitView()`，覆盖了这套相机参数；`fitView()` 是面向编辑浏览的全角色总览，因此所有景别都会看起来偏远。

此外，草图 PNG 捕获目前直接使用编辑视角相机。编辑视角是用户浏览场景的辅助相机，不应成为分镜成片参考图的取景来源；导出必须使用独立的场景摄像机机位，否则用户移动编辑视角后，保存图片会与取景画中画及布局中的分镜相机不一致。

## 目标

1. 有已保存布局时，3D 编辑器打开后保留布局相机，不再被默认总览覆盖。
2. 没有已保存布局时，仍使用 `fitView()` 帮助用户快速看到角色。
3. 草图 PNG 始终从独立场景摄像机的机位和当前 FOV 捕获，且不包含摄像机机身、取景辅助线、网格或选中描边。
4. 捕获结束后完整恢复编辑视角、画布尺寸、场景摄像机辅助显示和选择状态。
5. 保留“聚焦角色”按钮作为明确的编辑辅助操作，不改变其现有语义。

## 非目标

- 不修改 AI 自动构图 Prompt、景别档位或数据库 schema。
- 不自动重写历史草图文件；用户下一次打开并保存该镜头时，图片会按新的取景来源更新。
- 不改变后续视频关键帧使用已确认布局相机的既有链路。

## 设计

### 加载状态边界

`DramaBlocking3DPage` 在创建 viewer 时计算 `hasSavedLayout = layout.actors.length > 0`：

- `true`：调用一次 `loadLayout(layout)`，随后只清除选择，不调用 `fitView()`。
- `false`：调用 `fitView()` 建立空白草图的初始编辑视角。

这样 `fitView()` 只属于“没有布局时的初始浏览”和用户主动点击的编辑动作，不再覆盖服务器已经生成的景别相机。

### 导出相机边界

`blocking3dViewerApp.capturePng()` 在导出期间暂时把编辑器主相机设置为 `shotCameraPose`：

- 保存编辑相机的位置、旋转、FOV、裁剪面、视口和图层状态。
- 临时禁用场景摄像机实体和画中画，把主相机移动到场景摄像机的世界坐标与朝向，并使用同一个 FOV。
- 暂停辅助元素、渲染两帧清空上一帧辅助线，再捕获 1280×720 PNG。
- 在 `finally` 中恢复所有主相机状态和辅助状态，即使捕获或编码失败也不会污染编辑器。

使用主相机承载捕获可以继续复用现有 HDRI、阴影、景深和 16:9 导出流程，同时避免让画中画相机的矩形视口、构图辅助图层或较简化的后处理进入草图文件。

### 数据流

```text
shot.shotSize
    ↓
server resolveAutoPlanCameraFromIntent()
    ↓ layout3d.camera + derived shotCameraPose
DramaBlocking3DPage.loadLayout()
    ↓ 保留布局相机，不再 fitView 覆盖
blocking3dViewerApp.capturePng()
    ↓ 临时使用 shotCameraPose
blocking-sketch.png / storyboard card
```

## 错误处理

- 捕获前保存的相机状态必须在 `finally` 中恢复。
- 不新增数据库写入或恢复逻辑；上传失败仍沿用页面现有错误提示和未确认状态。
- 旧布局没有 `shotCamera` 时继续从其 `camera` 推导兼容机位。

## 验证

1. 客户端契约测试证明：加载已有布局的路径不再无条件调用 `fitView()`，无布局路径仍调用它。
2. 客户端 runtime 契约测试证明：捕获实现保存并恢复编辑相机状态，并把 `shotCameraPose` 写入捕获相机。
3. 运行客户端针对性测试和 TypeScript 类型检查。
4. 在本地 3D 草图页面打开真实分镜，检查前几个近景/特写镜头：相机预览中主体明显占据近景/特写对应的画面比例，编辑器重新加载后不会退回全角色远景；确认无控制台错误和失败网络请求。

## 长期规则

分镜的“编辑浏览相机”和“场景拍摄相机”是两个不同职责：前者服务空间编辑，后者决定草图及后续影像的取景。任何导出或用户可见的分镜参考图都必须从场景拍摄相机生成，不能直接抓取当前编辑视角。

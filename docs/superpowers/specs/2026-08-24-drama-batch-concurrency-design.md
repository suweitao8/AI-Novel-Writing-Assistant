# 短剧批量分镜画面并发优化设计

## Background

短剧工作室的“生成本集画面”和批量选镜头入口已经使用 worker pool，但服务端把关键帧批量并发固定为 3 路。当前本机图片链路中，带参考图的分镜会由图片 runtime 路由到 Codex 图片桥；Codex 桥明确把同时运行的图片 CLI 进程限制在最多 4 路。Grok Build 图片桥没有等价的 admission control，因此业务层不能把它视为无限并发。

当前任务进度已经持久化 `concurrency` 字段，但执行器仍直接读取固定常量，导致进度中的并发值不能真正决定恢复任务的 worker 数量。这既限制了吞吐，也让状态记录和实际执行存在偏差。

## Decision

### 1. 自动采用安全上限

关键帧批量任务的默认并发从 3 路提升到 4 路，并由服务端统一做 1–4 路裁剪。页面不新增并发选择器：对新手用户保持“点击批量生成即可自动使用安全最快档位”的默认路径，避免用户需要理解 provider 限制。

任务创建时把最终并发写入 `progress.concurrency`；任务恢复时读取并规范化该值，worker pool 使用规范化后的值，而不是绕过状态再次读取固定常量。历史任务没有该字段时回落到新的默认值；异常或越界值回落到安全范围内。

### 2. provider 边界

当前 Codex 图片桥的硬上限是 4 路，因此应用侧不允许超过 4 路。Grok Build 图片桥即使没有自身上限，应用侧也保持相同的 4 路保护，避免批量请求无界地拉起 CLI 进程。

参考图路由仍由现有图片 runtime 决定，不在批量 orchestrator 中复制 provider 分流逻辑。未来如果某个 provider 有更低的明确限制，只需在并发策略模块中增加 provider 上限，任务进度会记录裁剪后的实际值。

### 3. 状态、失败和重试

- 每个镜头继续由图片 runtime 写入 `generating`、`done` 或 `error`，前端以镜头自身状态显示生成中。
- 批量任务保留完整的 `failedShotIds` 和错误摘要；不增加自动盲目重试，避免在 provider 已接受请求但响应超时的情况下重复扣额度。
- 批量进度继续串行落库，保证 `done`、`failed`、费用和失败镜头列表不会因并发写入相互覆盖；并发 worker 只负责图片生成，最终状态仍等待所有 worker 完成后再收口。
- 页面批量状态显示实际并发路数，让用户能直接确认任务正在并发执行。

### 4. Verification

增加/更新以下契约：

- worker pool 在配置为 4 时最多同时执行 4 个镜头，并覆盖空列表、越界值和历史进度恢复的并发裁剪。
- 新建关键帧批量任务写入并发 4，恢复任务使用持久化并发值。
- 前端批量状态显示 progress 中的实际并发路数。
- 服务端类型检查、关键帧批量相关测试和客户端相关测试通过；不进行真实订阅图片压测，只验证本地 bridge health 与静态并发边界，避免测试消耗额度。

## Non-goals

- 不改变图片 provider 路由、提示词、参考图选择或单镜头生成流程。
- 不把视频、TTS 批量任务改成并发；它们各自有独立的外部服务和成本约束。
- 不新增数据库字段，不删除已有批量任务，不重置数据库。
